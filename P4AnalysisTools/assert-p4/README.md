# ASSERT-P4

We evaluated the released ASSERT-P4 artifact by examining the C verification model generated for our amplification program.

## Source

- Paper: *Uncovering Bugs in P4 Programs with Assertion-based Verification*
- Repository: https://github.com/LucasMFreire/assert-p4

## Compatibility

The released artifact expects an older p4c JSON representation that is incompatible with the output of current p4c versions.

We therefore use the `convert_assertp4_json.py` script to normalize the current compiler JSON into the representation expected by ASSERT-P4. We validated this conversion using the Dapper case study included with ASSERT-P4 before applying it to our program.

## Input

The `input/` directory contains the P4 amplification program and its compiler-generated JSON representation.

## Generating the C Model

Normalize the JSON generated from ``p4c``-compilation of the P4 file:

```bash
python3 src/convert_assertp4_json.py \
  input/SoK_Amp_P4_16.p4.json \
  /input/SoK_Amp_P4_16.NEW.json
````

Generate ASSERT-P4's C verification model:

```bash
python2 src/P4_to_C.py \
  /input/SoK_Amp_P4_16.NEW.json \
  > /output/SoK_Amp_P4_16.c
```

The resulting C file is included in the `output/` directory.

## Evaluation

Due to compatibility issues with the released artifact and its legacy dependencies, we did not complete the subsequent KLEE execution stage. Our evaluation therefore examines the C model generated by ASSERT-P4 rather than reporting an end-to-end verification result.

Inspection of the generated model shows that cloning and recirculation are represented individually, but the execution harness invokes the parser, ingress, egress, and deparser only once. A recirculation request therefore does not cause another parser/ingress traversal.

Consequently, the model cannot represent the repeated clone-recirculate feedback responsible for sustained amplification.
